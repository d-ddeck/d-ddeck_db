# 개선 검토 (2026-09-26, 서버·앱 1.0.5 기준)

백엔드(FastAPI) · Flutter 앱 · 배포/운영 · 구 서버(CS_Record) 대비 기능 공백, 네 갈래로 전체를 점검한 결과입니다. 항목마다 파일:줄 근거를 적었고, 높음 등급은 코드에서 재확인했습니다. 처리한 항목은 맨 앞 칸에 ✅ 와 버전을 적어 주세요(구 서버 `개선검토.md` 방식).

초기 검토 당시 검사 결과(최종 검증은 작업 기록 4 참고): 스모크 테스트 207건 · 구 서버 규칙 145건 · Flutter 테스트 71건 모두 통과. `dart analyze` info 4건, `ruff --select F,E9` 10건(테스트 스크립트의 불필요한 f-string 등, 실행에 영향 없음). 즉 **정상 경로는 잘 돌고, 문제는 대부분 정상 경로 밖**(삭제된 것 조회, 권한 경계, 오프라인, 새 설치, 복원)에 있습니다.

## 잘 되어 있는 것 (다시 점검할 필요 없음)

- JWT 알고리즘 고정·`typ` 검사, refresh 토큰 해시 저장, 매 요청 계정 상태 재확인, 계정 열거 방지 문구, bcrypt 72바이트 선해시, 비밀번호 변경 시 전 세션 회수.
- 업로드 저장명 UUID + 파일명 정화 + 루트 검사, Content-Disposition 한글 정상, `.env`·DB·storage·VPN conf 모두 gitignore.
- 감사 행이 호출자 트랜잭션에 실림, 비밀번호류 diff 제외. SQLite SAVEPOINT 처방이 실제로 롤백됨(스크립트로 확인).
- 원인 행 vs 대응 건수, 재고 상태 규칙(store/as/clear/free), 폐점 회수, 렌탈 저장→'렌탈 중' 기본 경로, 채번 재시도, 일괄 이동 건별 롤백, 리마인더 offset 유지, 대체공휴일 계산(2025·2026 실제와 일치).
- 앱: 401 갱신 단일화(`_refreshInFlight`), access 토큰 메모리만·refresh 는 secure storage, 자동 로그인 끄면 디스크 미저장, VPN 개인키 비노출, 저장 중 중복 제출 방지 전 폼 일관, `mounted` 검사 일관, 등록/수정 후 복귀 시 reload 패턴 일관.
- 배포: 설치 스크립트가 SECRET_KEY·관리자 비번 난수 생성, `.env` 600, rsync 가 `.env`/storage/DB 보존, SQLite `.backup` API 사용, 테스트 통과 후에만 빌드.

## 정책 결정이 필요한 것 (코드보다 먼저 정할 것)

1. **결정·반영: 폐점·매장 장비 설정은 ADMIN 이상** — 사용자 답변 기준(1-5). 세트 추가·수정·삭제도 동일.
2. **매장 상태 저장(개점일·메모)을 일반 사용자에게 허용할지** — 구 서버는 허용, 신 서버는 ADMIN.
3. **결정·반영: 폐점 매장은 경고 후 허용** — 접수·장비 등록/이동·장비 설정 화면에서 확인(2-21).
4. **백업 후 전원 끄기 + RTC 기동 부활 여부** — 구 서버 방식. 개선검토 4-4 가 지적한 "01~08시 서비스 공백·RTC 단일 실패점" 단점도 함께.
5. **관리자 직접 계정 생성** vs 현행 가입 → 승인. 운영 방식이 바뀌었으니 팀에 안내 필요.
6. **결정·반영: 여러 기기 로그인 허용 + 세션 조회·종료 화면** — 사용자 답변 기준.
7. **반영: 앱 배포는 Windows·Android, 서버는 Ubuntu** — Linux 데스크톱은 개발용 빌드 대상.
8. **결정·반영: 도메인·사내망/VPN CIDR 미정** — 설치 시 입력. 인증서는 운영 준비 후 적용(4-12).

## 작업 기록 4 — 2026-09-26, 3~5순위 완료 (미배포)

사용자 요청 범위의 **남은 64개 검토 항목을 코드·CI·문서에 반영**했다. 현재 표의 **127개 항목 모두 구현 완료**이며, 실제 서버 배포 완료를 뜻하지 않는다. 앞선 기록의 “남음/일부 반영”은 당시 상태다. 운영 DB·기존 서비스·구 서버 원본을 변경하지 않았다.

사용자 결정은 다음과 같이 적용했다.

- 동시 로그인은 여러 기기 허용. 세션을 조회하고 선택한 기기를 즉시 로그아웃할 수 있다.
- 원격 백업·Firebase 기존 설정 없음: 설정 가능한 코드, CI 입력, 운영 준비 문서를 구현했다.
- HTTPS 도메인·CIDR 미정: 설치기 `--https` 또는 별도 설정 도구에서 입력한다.
- Android 기존 키 없음: 앞서 구현한 키 준비·CI 등록 절차를 유지한다.

- Flutter **109건 통과**, 실서버 데모 계정이 필요한 **19건 건너뜀**, `flutter analyze` 오류·경고·info 없음. 영문 임시 경로의 동일 소스로 검증했다. 동시 401 갱신·refresh 실패/403·알람 유지·저장소·프로필 검증·알림/계정 화면·달력 레인/드래그·이미지 축소·필터 분리를 포함한다.
- 배포 도구 **20건 통과**: SQLite 백업/복원, ZIP·공간·원격 실패, TLS 입력, 실제 임시 DB/코드/첨부 롤백, 기존 DB 위치 이전, PostgreSQL 복원 명령, 갱신 중단 순서를 검사했다. OS 서비스 변경은 모의 명령을 사용했다.
- 구 데이터 이관 dry-run에서 실제 대상 DB가 생성되지 않음을 확인했다. 합성 이관 자료를 두 번 적용해 중복 없음과 수정자·빈 게시판·비활성 상태 보존도 확인했다.
- Ruff, 셸 구문, 버전 일치, diff 공백 검사와 서버 패키지의 비밀 파일 제외를 확인했다.

### 외부 설정 후 실행할 사항

코드 구현의 남은 항목은 없지만 **운영 서버 배포는 하지 않았다.** 다음 실행은 운영 자원 준비 후 필요하다.

1. Android 고정 서명키 생성·CI Secrets 등록과 Windows/Android 릴리스 빌드·실기기 점검.
2. Firebase 프로젝트/서비스 계정 설정 후 실제 Android 수신 확인.
3. rclone remote/설정 파일 등록 후 실제 외부 업로드·검증·원격 보존 확인.
4. 도메인·허용 CIDR·신뢰 인증서 입력 후 실제 nginx/systemd/방화벽과 클라이언트 HTTPS 접속 확인. 현재 앱의 기본 신뢰 저장소에 없는 사설 CA는 별도 앱 신뢰 설정과 검증이 필요하다.
5. 운영 백업을 확보한 뒤 서버·앱 동시 갱신, 새 리비전 적용, 재로그인 안내 및 복원 드릴. Windows 서버 호환 설치/작업 스케줄러는 실제 Windows에서 추가 검증한다.
