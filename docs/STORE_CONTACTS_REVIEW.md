# 매장 연락 정보와 대응일지·견적서 연동

검토 브랜치: `feature/service-work-types` (운영 병합 전)

## 사용 방법

1. **장비 매장 → 매장 선택 → 수정**에서 `매장 연락 정보`에 매장 담당자, 연락처, 주소를 입력하고 저장합니다. 기존 매장 수정 권한(관리자 이상)을 유지합니다.
2. 서비스 대응일지 작성 화면에서 매장을 선택하면 세 항목이 자동 입력됩니다. 매장 상세에서 대응일지를 작성해도 동일하게 적용됩니다. 건별로 직접 수정할 수 있습니다.
3. **저장 후 견적서 작성** 또는 대응 상세의 **견적서**에서 새 견적을 작성하면 수신자 담당자·연락처·주소에 대응일지의 값이 자동 입력됩니다. 대응일지에 값이 없는 항목은 현재 매장 정보로 보완합니다.
4. 견적을 저장하면 기존 방식대로 새 버전의 PDF가 생성됩니다. 기존 버전을 바탕으로 수정하면 해당 버전의 수신자 정보를 유지합니다.

## 보존 규칙

- 매장 기본 정보를 수정해도 기존 대응일지의 저장된 연락 정보는 바뀌지 않습니다.
- 기존 대응일지 수정 화면은 저장 당시 값을 표시합니다. 다른 매장으로 변경하면 새 매장의 연락 정보를 가져옵니다.
- 이미 저장된 견적서 및 PDF는 변경하지 않습니다.
- API에서 연락 항목을 생략하면 매장 값을 가져오며, 명시적인 null/빈 문자열은 그대로 저장합니다. 같은 매장으로 대응일지를 수정하는 경우 생략된 연락 항목은 유지합니다.
- 담당자 150자, 연락처 50자, 주소 300자. 모두 선택 항목입니다.

## DB 및 검증

- Alembic `d527a318fc40`: stores에 contact_name/contact_phone/address, service_tickets에 contact_name을 nullable로 추가합니다. 기존 데이터는 유지합니다.
- 기존 서버에는 앱과 서버를 함께 업데이트하고 DB 백업 후 `alembic upgrade head`가 필요합니다.
- 이번 적용 대상은 포트 18000의 별도 검증용 DB이며, 운영 서버/DB는 변경하지 않았습니다.
- 서버 연락 정보 테스트: 저장/삭제, 자동 입력, 직접 입력 우선, 매장 변경, 이전 대응 정보 보존, 견적 기본값, 길이 제한, 실제 PDF의 연락 정보 출력 및 매장 변경 후 PDF 불변성 검증.
- 견적 회귀 테스트: PDF 생성, 버전 불변성, 동시 수정, 권한 및 다중 페이지 검증.
- 마이그레이션 테스트 통과, 서버 smoke 254개 통과.
- Flutter analyze 통과, Flutter 테스트 237개 통과/외부 서버 계약 테스트 19개 건너뜀.
- Linux 검증용 앱 빌드 완료. 기존 `d-ddeck 업무구분 검증` 바로가기를 닫았다가 다시 열어 확인합니다. Android/Windows 실기기 검증은 별도입니다.
