# 작업 정리 — 서비스 접수 단계화·캘린더 연동·백업 후 전원 끄기

작성일: 2026-10-02
기준 버전: 1.0.24 (커밋 `f809a97`) 이후 미커밋 변경

## 요약

| 기능 | 내용 | 서버 변경 |
|---|---|---|
| 서비스 건 ↔ 캘린더 연동 | AS 상세에서 일정 등록, 연결 일정 목록 | API 추가 |
| 신규 접수 단계화 | 내용 접수 → 견적서 → 일정·처리 상태, 마지막에 한 번에 저장 | API 확장 |
| 종결 입력 화면 내 표시 | 접수 마지막 단계에서 종결 시 팝업 없이 바로 입력 | 없음 |

## 1. 서비스 건 ↔ 캘린더 일정 연동

### 기능
- **AS 상세 > 연결 일정** 카드
  - 이 건에서 등록한 일정 목록(반복 일정은 원본 1건만)
  - **일정 등록**: 서비스 건 내용으로 미리 채운 일정 등록 화면을 연다
  - 일정을 누르면 기존 일정 상세 시트(수정·삭제)
- 미리 채우는 값

  | 항목 | 값 |
  |---|---|
  | 제목 | `[AS] 매장명 · 작업구분` |
  | 장소 | 현장 주소, 없으면 매장명 |
  | 설명 | 접수번호 + 접수 내용 |
  | 참석자 | 배정 담당자 |
  | 날짜 | 처리 기한이 남아 있으면 그 날, 아니면 오늘 |
- 기존 건 수정 화면에는 **저장 후 일정 등록** 버튼을 둔다.

### 서버
- `events.service_ticket_id` 컬럼은 기존에 있었으나 쓰이지 않았다. 이를 활용한다.
- `POST /calendar/events`: `service_ticket_id`가 없거나 삭제된 건이면 `404 NOT_FOUND`
- 신규 `GET /calendar/service-tickets/{ticket_id}/events`
  - 볼 수 있는 캘린더의 일정 + 본인이 만들었거나 참석하는 일정
  - 비공개 일정 가림 규칙은 일정 목록과 동일(공통 함수 `_masked_events`로 분리)

## 2. 신규 접수 단계화

### 흐름
1. **내용 접수** — 기존 접수 폼. "접수 저장 · 다음: 견적서 작성"을 눌러도 저장하지 않는다.
2. **견적서 작성** (건너뛰기 가능) — 견적서를 임시로 작성. 품목 수·금액 표시, 수정·삭제 가능
3. **일정 · 처리 상태**
   - 일정 추가(건너뛰기 가능) — 임시 목록에 담고 개별 삭제 가능
   - 처리 상태 **진행중 / 종결** 선택
   - **종결** 선택 시 화면에 바로 표시: 서비스 내용(필수), 서비스인원(필수, 접수 폼 선택값으로 시작), 서비스일
   - 버튼: "진행중으로 접수 저장" / "종결로 접수 저장"

### 저장 시점
- 마지막 버튼을 누를 때 **접수 건 + 처리 상태(종결이면 서비스일 포함)** 를 한 번의 요청으로 저장한다.
- 이어서 임시 견적서와 일정을 그 건에 등록한다. 이 단계에서 실패하면 접수는 유지하고 "AS 상세에서 다시 등록" 안내를 띄운다.
- 1단계로 돌아가면 입력 내용은 유지된다. 견적서·일정을 담아 둔 상태면 사라진다는 확인을 받는다.
- 기존 접수 폼의 "저장 상태" 드롭다운은 제거했다(3단계로 이동).
- 첨부파일은 기존처럼 접수 저장 직후 업로드하며, 실패하면 폼에서 재시도한다.

### 서버
- `POST /service/tickets`: `completed_at` 추가. `initial_status=COMPLETED`일 때 서비스일로 쓴다(비우면 저장 시각).
- 신규 `GET /service/quotations/defaults?store_id&customer_name&contact_name&contact_phone&site_address`
  - 접수 저장 전 견적서 기본값. 기존 `/service/tickets/{id}/quotations/defaults`와 같은 규칙(공통 `_defaults`)

### 앱 구조
- `QuotationEditPage.draft` — 서버에 보내지 않고 작성한 본문을 돌려준다.
- `EventFormPage(onDraft:)` — 서버에 보내지 않고 `EventDraft`를 돌려준다. `CalendarRepository.createDraft`로 나중에 등록
- 종결 입력 창(AS 상세의 상태 변경 다이얼로그)은 `status_change_dialog.dart`로 분리했다. AS 상세에서 그대로 사용

## 3. 백업 후 PC 전원 끄기

### 기능
관리 > Google 공유 드라이브 백업 > **백업 후 PC 전원 끄기**

- ON/OFF 스위치. 도우미가 설치되지 않은 PC에서는 켤 수 없고 설치 명령을 안내한다.
- ON일 때만 표시
  - 끄기 전 유예: 1·3·5·10·15·30·60분 (기본 5분)
  - 다시 켤 시각 (기본 07:00, 한국 시간)
- 유예 중: "○시에 꺼지고 ○시에 다시 켜집니다" + **이번만 취소**. 관리자(ADMIN 이상)에게 앱 알림
- 마지막 전원 끄기 시각, 다시 켜짐 예정, 건너뛴 사유 표시

### 동작 규칙
- **예약 시각에 제때(15분 이내) 시작한 자동 백업**이 Drive 업로드까지 성공한 경우에만 끈다.
- 끄지 않는 경우: 수동 백업, 실패한 백업, PC가 켜진 직후 밀려서 실행된 백업(켜짐 → 밀린 백업 → 다시 꺼짐 반복 방지)
- 다시 켤 시각: 끄는 시각에서 최소 10분 뒤 처음 오는 지정 시각
- 유예 종료 후 10분 넘게 지난 요청(정전·재시작)은 실행하지 않고 건너뛴다.
- 기능을 끄면 진행 중인 카운트다운도 취소된다.

### 구조
서버는 일반 계정 + `NoNewPrivileges`로 실행되어 직접 PC를 끌 수 없다.

```
서버(drive_backup)              루트(systemd)
 유예 종료 → backups/.power/request 에 켜질 시각(UNIX 초) 기록
                                 ddeck-power.path 가 파일 감지
                                 → ddeck-power.service
                                 → /usr/local/sbin/ddeck-power-off
                                    · 심볼릭 링크/다른 계정 소유/형식 오류 거부
                                    · 켜질 시각이 5분~48시간 범위 밖이면 거부
                                    · rtcwake -m no -t <시각> → systemctl poweroff
```

- 도우미는 서버 계정이 수정할 수 없는 `/usr/local/sbin`에 설치한다.
- 서버는 유닛 파일이 이 서버의 요청 경로를 감시하는지 확인해 `ready` 여부를 표시한다.

### 설치
```bash
python3 deploy/power_helper.py                   # 미리 보기
sudo python3 deploy/power_helper.py --install    # 설치 (BACKUP_ROOT 사용 시 --root 지정)
sudo python3 deploy/power_helper.py --uninstall  # 제거
```
이 서버 PC에는 2026-10-02 설치 완료(`ddeck-power.path` 활성, 경로 일치 확인).

### API
- `GET /admin/drive-backup` 응답에 `power` 추가: `enabled, grace_minutes, wake_hour, wake_minute, ready, pending, last_requested_at, last_wake_at, note`
- `PUT /admin/drive-backup/power` `{enabled, grace_minutes(1–60), wake_hour(0–23), wake_minute(0–59)}` — 도우미 없이 켜면 `409 POWER_HELPER_MISSING`
- `POST /admin/drive-backup/power/cancel` — 이번 회차만 취소

### 하드웨어 확인 결과
- RTC `rtc_cmos`, 깨우기 활성, `rtcwake`의 `off` 모드 지원, RTC는 UTC
- **완전히 꺼진 상태에서 켜지는지는 미확인** — BIOS 설정에 따라 다르다.

## 남은 확인 사항

1. **서버 재시작** — 새 API 반영: `sudo systemctl restart ddeck.service`
   - 재시작 전에는 연결 일정 목록·접수 전 견적서가 오류, 종결 서비스일이 무시됨
2. **실기 확인** — 앱 화면을 직접 눌러 확인하지 못했다. 접수 3단계 흐름과 연결 일정을 앱에서 확인 필요
3. **전원 켜짐 시험** — 사용하지 않는 시간에 1회
   - `sudo rtcwake -m off -s 600` (지금 끄고 10분 뒤 켜기) 또는 백업·켤 시각을 가깝게 설정
   - 켜지지 않으면 BIOS의 RTC 켜짐(Wake on RTC, Resume by Alarm 등) 활성화
4. 전원이 꺼져 있는 동안 앱 접속과 VPN이 끊긴다는 점을 사용자에게 공지
5. 정전 후 자동 켜짐은 별도 BIOS 설정(AC Power Recovery)
6. 작업 중 이 작업과 무관한 `worklog_page.dart`, `service_stats_page.dart` 변경이 작업 트리에 있다(다른 작업). 커밋 시 분리 필요
