1. 현재 운영 환경

항목 현재 값
운영체제 / 실행 계정 Ubuntu / leemoon
프로젝트 /home/leemoon/바탕화면/d-ddeck_db
서버 작업 폴더 /home/leemoon/바탕화면/d-ddeck_db/backend
서비스 이름 ddeck.service
서비스 설정 /etc/systemd/system/ddeck.service
Python 가상환경 backend/.venv-linux
서버 설정 backend/.env
DB SQLite, backend/ddeck.db
첨부파일 backend/storage/
사내 앱 접속 주소 http://192.168.0.20:8000
서버 자체 상태 확인 http://127.0.0.1:8000/healthz
검증용 서버 127.0.0.1:18000, 운영과 별도 DB
조사 시 상태 서비스 active, 부팅 자동 시작 enabled, 응답 버전 1.0.13

이 설치본은 바탕화면 프로젝트에서 실행됩니다. /opt/ddeck에 설치하는 신규 서버 패키지와 경로가 다릅니다. 현재 서버에는 /opt/ddeck 전용 deploy/update.sh, deploy/backup.sh를 그대로 실행하지 마세요. 새 PC의 표준 설치는 마지막 장을 참고하세요.

휴대폰·Windows 앱의 서버 주소에는 192.168.0.20을 사용합니다. 다른 기기에서 127.0.0.1을 입력하면 그 기기 자신에게 접속하므로 서버에 연결되지 않습니다. IP가 변경됐다면 공유기의 DHCP 예약과 앱 주소를 함께 확인하세요.

2. 자주 사용하는 명령

목적 터미널 명령
중지된 서버 시작 sudo systemctl start ddeck
상태 확인 systemctl status ddeck --no-pager -l
백업 후 재시작 ddeck-restart
백업만 실행 ddeck-restart --backup-only
서버 중지 sudo systemctl stop ddeck
부팅 자동 시작 설정 sudo systemctl enable ddeck
자동 시작 여부 확인 systemctl is-enabled ddeck
최근 로그 50줄 journalctl -u ddeck -n 50 --no-pager
실시간 로그 journalctl -u ddeck -f
응답 / 버전 확인 curl -fsS --max-time 5 http://127.0.0.1:8000/healthz

systemctl status 화면이 페이지 형태로 열리면 q로 나옵니다. 실시간 로그는 Ctrl+C로 종료하며, 로그 보기 종료는 서버를 중지하지 않습니다.

sudo systemctl restart ddeck 자체에는 백업 기능이 없습니다. 일상 재시작에는 ddeck-restart를 사용하세요. ddeck-restart는 이번에 현재 PC에 추가한 명령이며, 1.0.13 배포 파일에 원래 포함된 명령은 아닙니다.

3. 서버 시작·종료와 정상 확인

3.1 중지 상태에서 시작

sudo systemctl start ddeck
systemctl status ddeck --no-pager -l
curl -fsS --max-time 5 http://127.0.0.1:8000/healthz

정상 기준은 Active: active (running)과 아래 JSON입니다. 시작 직후 아직 준비 중이면 잠시 후 curl을 다시 실행합니다.

{"status":"ok","version":"1.0.13"}

그다음 같은 사내망의 앱에서 로그인하고 목록을 조회합니다. /healthz는 기본 응답 확인이므로 로그인·DB 조회까지 대신 검증하지 않습니다.

3.2 부팅 시 자동 실행

현재는 이미 설정돼 있습니다. 새로 등록하거나 해제했을 때만 아래 명령을 사용합니다.

sudo systemctl enable ddeck
systemctl is-enabled ddeck

enabled면 부팅 자동 시작 대상입니다. enable만으로 지금 중지된 서버가 시작되는 것은 아니므로 필요하면 start도 실행합니다.

3.3 서버 중지

sudo systemctl stop ddeck
systemctl is-active ddeck

정상 중지 시 inactive입니다. 중지 중에는 앱 로그인·저장·동기화와 서버 스케줄러가 작동하지 않습니다. 관리 작업 전에 사용자에게 시간을 안내하세요. 운영 서비스가 켜져 있는 동안 같은 DB로 별도 uvicorn 서버를 실행하지 않습니다.

4. 진행률을 보며 백업 후 재시작

ddeck-restart

진행 예:

DB 복사 [###############---------------]  50%
DB 복사 [##############################] 100%
백업 무결성 검사 중...
백업 완료: /home/leemoon/.local/share/ddeck-backups/restarts/...
서버 DB 구조 확인 중...
백업 검증 완료. 서버 재시작 중...
서버 정상 실행: 1.0.13

처리 순서는 서비스 경로 확인 → 관리자 인증 → SQLite 온라인 백업 → 무결성 검사 → DB 구조 검사 → 재시작 → 최대 30초 정상 응답 확인입니다.

  • 게이지는 실제 DB 페이지 복사 비율입니다. 100% 뒤에도 무결성 검사가 남아 있습니다.
  • DB가 작으면 게이지가 빠르게 완료됩니다.
  • 백업·설정 복사·DB 구조 검사 실패 시 재시작하지 않습니다.
  • 이 명령은 의존성 설치나 DB 마이그레이션을 자동 실행하지 않습니다.
  • Ctrl+C로 중단했다면 서비스 상태를 확인합니다. 이미 재시작 단계였다면 서비스 상태가 바뀌었을 수 있습니다.
  • 현재 SQLite 설치본과 서비스 이름 ddeck, 포트 8000 기준입니다.

명령을 찾지 못할 때:

~/.local/bin/ddeck-restart

프로젝트에서 직접 실행할 수도 있습니다.

cd '/home/leemoon/바탕화면/d-ddeck_db'
./deploy/restart-with-backup.sh

5. 백업 범위·보관과 전체 백업

5.1 일상 DB 백업

ddeck-restart --backup-only

서버를 재시작하지 않으며 관리자 인증도 요청하지 않습니다. 백업 위치:

/home/leemoon/.local/share/ddeck-backups/restarts/
  restart-날짜-시각/
    ddeck.db
    backend.env
    manifest.json

DB에는 계정, 업무 기록, 매장 정보와 저장한 견적 PDF 등이 포함됩니다. backend.env에는 비밀 설정이 있으므로 백업 폴더 전체를 공개 저장소나 채팅에 올리지 않습니다. 폴더 권한은 0700, DB·설정 파일은 0600입니다.

업로드한 사진·일반 첨부파일은 backend/storage에 있으므로 위 DB 백업에 포함되지 않습니다. 온라인 백업 시점 이후의 변경도 해당 백업에는 포함되지 않습니다. 파일 백업까지 필요한 업데이트·복구 전에는 전체 백업을 수행하세요.

백업은 매번 새 폴더에 저장하며 자동 삭제하지 않습니다. 정기적으로 용량과 보존본을 확인하고 외장 디스크나 승인된 NAS로 복사하세요. 같은 디스크의 백업만으로는 디스크 고장에 대비할 수 없습니다. 현재 자동 원격 전송이나 주기 실행이 설정됐다고 가정하지 마세요.

5.2 DB·첨부·설정의 전체 백업

아래 블록은 현재 설치 경로와 DB 파일 기준입니다. 서버를 중지하고 백업합니다. 한 단계라도 실패하면 중단하며 서버는 중지 상태로 남습니다. 출력된 백업 폴더를 기록하세요. 완료 후에도 점검·업데이트를 이어갈 수 있도록 자동 시작하지 않습니다.

bash <<'BASH'
set -euo pipefail
umask 077
cd '/home/leemoon/바탕화면/d-ddeck_db'
sudo systemctl stop ddeck
if systemctl is-active --quiet ddeck; then
  echo '서버가 아직 실행 중입니다.' >&2
  exit 1
fi
DDECK_SNAPSHOT="$(mktemp -d "$HOME/ddeck-full-$(date +%Y%m%d-%H%M%S)-XXXXXX")"
backend/.venv-linux/bin/python deploy/sqlite_backup.py snapshot \
  backend/ddeck.db "$DDECK_SNAPSHOT/ddeck.db"
cp -a backend/.env "$DDECK_SNAPSHOT/backend.env"
cp -a backend/storage "$DDECK_SNAPSHOT/storage"
cp -a /etc/systemd/system/ddeck.service "$DDECK_SNAPSHOT/ddeck.service"
git rev-parse HEAD > "$DDECK_SNAPSHOT/code-commit.txt"
backend/.venv-linux/bin/python -m pip freeze > "$DDECK_SNAPSHOT/python-packages.txt"
(cd "$DDECK_SNAPSHOT" && sha256sum ddeck.db > SHA256SUMS)
printf '전체 백업 완료: %s\n서버는 중지 상태입니다.\n' "$DDECK_SNAPSHOT"
BASH

추가 수동 서버나 외부 DB 기록 작업도 중지한 상태에서 실행합니다. .env의 DB·첨부 경로를 변경했다면 이 블록의 경로도 맞춰야 합니다. 단순 백업 목적이었다면 완료 후 sudo systemctl start ddeck으로 시작하고 /healthz를 확인합니다.

6. 서버 업데이트와 DB 마이그레이션

6.1 재시작과 업데이트의 차이

작업 하는 일 하지 않는 일
systemctl restart 현재 코드로 프로세스 재실행 백업, 코드 다운로드, 의존성 설치, DB 변경
ddeck-restart 백업·검사 후 프로세스 재실행 코드 다운로드, 의존성 설치, DB 변경
서버 업데이트 코드·의존성·DB 구조를 버전에 맞춤 앱 설치 파일의 자동 배포는 별도
앱 업데이트 Windows·Android 앱을 교체 서버 코드나 DB 구조 변경

1.0.13은 업무 구분·견적 이력·연락 정보용 DB 변경이 필요합니다. 최종 리비전은 d527a318fc40입니다. DB가 이전 상태면 시작 전 검사에서 Target database is not up to date가 발생해 서비스가 시작되지 않습니다.

6.2 현재 바탕화면 설치본 업데이트 순서

  1. 작업 시간을 안내하고 릴리즈 노트에서 DB 변경 여부를 확인합니다.
  2. 위의 전체 백업을 완료합니다. 서버는 중지된 상태로 둡니다.
  3. 프로젝트의 git status --short로 미커밋 작업을 확인합니다. 개인 수정·양식 파일을 삭제하거나 강제로 덮어쓰지 않습니다.
  4. 승인된 릴리즈 코드를 반영합니다. 현재처럼 master로 운영하는 경우 아래 명령은 원격 기본 브랜치를 가져옵니다. 릴리즈 이후 미배포 커밋이 있는지 확인한 경우에만 이 경로로 반영하고, 특정 버전 배포가 필요하면 운영 담당자가 그 버전의 체크아웃을 준비합니다.
cd '/home/leemoon/바탕화면/d-ddeck_db'
git status --short
git fetch origin --tags
git log -5 --oneline origin/master
git pull --ff-only origin master

충돌·인증 실패가 있으면 해결 전 다음 단계를 진행하지 않습니다. reset --hard로 해결하지 마세요.

  1. 의존성과 DB 구조를 갱신합니다. 서비스 중지와 전체 백업이 완료된 뒤 한 블록으로 실행합니다. Python 작업에는 sudo를 붙이지 않습니다.
bash <<'BASH'
set -euo pipefail
cd '/home/leemoon/바탕화면/d-ddeck_db/backend'
if systemctl is-active --quiet ddeck; then
  echo '먼저 서버를 중지하고 전체 백업을 완료하세요.' >&2
  exit 1
fi
.venv-linux/bin/python -m pip install -r requirements.txt
env -u DEBUG -u DATABASE_URL -u ENVIRONMENT \
  .venv-linux/bin/python -m alembic upgrade head
env -u DEBUG -u DATABASE_URL -u ENVIRONMENT \
  .venv-linux/bin/python -m alembic check
BASH

성공 기준은 명령 종료 성공과 No new upgrade operations detected.입니다. 실패하면 서버를 중지 상태로 두고 로그를 확인합니다. 환경변수 제거 옵션은 터미널의 임시 설정 대신 서비스와 같은 backend/.env를 사용하기 위한 것입니다.

  1. 서비스를 시작하고 DB 조회까지 확인합니다.
sudo systemctl reset-failed ddeck
sudo systemctl start ddeck
systemctl status ddeck --no-pager -l
curl -fsS --max-time 5 http://127.0.0.1:8000/healthz
  1. 앱에서 로그인, 기존 대응 조회, 매장 조회, 견적 PDF 열기를 확인한 뒤 사용자에게 완료를 안내합니다.

마이그레이션 리비전 숫자만 바꾸는 alembic stamp는 일반 업데이트 명령이 아닙니다. 시작 오류를 피하려고 임의로 사용하면 실제 테이블과 버전 기록이 달라질 수 있습니다. 오래된 DB의 최초 전환은 별도 검증 도구와 기존 서버 등록 안내를 따릅니다.

7. Windows·Android 앱 업데이트 배포

GitHub 릴리즈 게시, 운영 서버 업데이트, 사내 앱 자동 업데이트 게시를 각각 구분합니다. 서버를 업데이트한 뒤 앱 업데이트 파일을 게시하세요.

릴리즈 다운로드: GitHub Releases

파일 용도
ddeck-setup-버전.exe Windows 앱 설치
ddeck-버전-arm64.apk Android 앱 설치
ddeck-server-버전.run /opt/ddeck 표준 서버 설치/갱신
update-manifest.json 앱 업데이트 파일 검증용 서명 정보
SHA256SUMS 배포 파일 체크섬

현재 서버에 1.0.13 앱 업데이트 파일을 게시하려면, GitHub CLI가 인증된 설치 소유자 계정으로 다음을 실행합니다.

cd '/home/leemoon/바탕화면/d-ddeck_db'
bash deploy/sync_client_updates.sh v1.0.13

스크립트는 해당 릴리즈의 앱 파일을 내려받아 서명·크기·해시를 검증하고 서버의 첨부 저장소 아래 client-updates에 게시합니다. 이미 같은 파일이 게시돼 있으면 검증 후 종료합니다. .env와 GitHub 인증이 필요하며 sudo로 실행하지 않습니다.

앱에서는 재실행 또는 설정의 업데이트 확인을 사용합니다. Android는 OS 설치 승인이 필요합니다. 기존과 다른 서명 키로 APK를 만들면 정상적인 덮어쓰기 업데이트가 불가능할 수 있으므로 운영 키를 유지합니다. 자세한 절차는 Android 서명 안내를 참고하세요.

8. 견적서·매장 정보 운영

  • 매장 상세 → 수정에서 담당자·연락처·주소를 관리합니다. 기존 수정 권한을 유지합니다.
  • 새 대응일지에서 매장을 선택하면 연락 정보가 자동 입력되고 건별로 수정할 수 있습니다.
  • 새 견적서에는 대응일지의 연락 정보가 먼저 들어가며, 빈 항목은 매장 정보로 보완합니다.
  • 매장 기본 정보를 바꿔도 과거 대응일지와 이미 저장된 견적 PDF는 바뀌지 않습니다.
  • 견적 수정은 새 버전을 만들고 이전 파일을 보존합니다. PDF 원본이 DB에 저장되므로 DB 용량도 증가합니다.

회사 양식의 공급자·입금계좌·서명은 서버별로 설정합니다. 회사 원본·서명·계좌는 공개 배포 파일에 포함되지 않습니다. 먼저 실제 양식 파일 경로로 바꿔 검증합니다.

cd '/home/leemoon/바탕화면/d-ddeck_db/backend'
env -u DEBUG -u DATABASE_URL -u ENVIRONMENT \
  .venv-linux/bin/python scripts/import_quotation_defaults.py '/실제/견적서.xlsx'

입력 파일과 대상 서버를 확인한 뒤 동일 명령 끝에 --apply를 붙여 저장합니다. 새 견적에 서명이 보이지 않으면 기본값 가져오기 여부와 공급자 회사명·대표자 이름 일치를 확인합니다. 기존 PDF는 설정 변경으로 갱신되지 않습니다.

로그 공유 시 비밀번호, 토큰, .env 내용, 고객 연락처 등은 제외합니다. 오류 발생 시각, 실행 명령, 서비스 상태, 마지막 오류 로그, 서버/앱 버전을 함께 남기면 원인 확인이 쉽습니다.

10. 백업 복구와 롤백

복구는 현재 데이터를 백업 시점으로 되돌립니다. 백업 이후 등록한 기록은 복구본에 없으므로 먼저 사용자와 복구 시점을 확인합니다. 운영 복구 전에 별도 시험 DB에서 검증하는 것이 원칙입니다.

10.1 복구 전 준비

  1. 서버와 수동 DB 기록 작업을 모두 중지합니다.
  2. 현재 상태도 5장의 전체 백업으로 별도 보관합니다.
  3. 복구할 백업의 날짜·원본 경로·무결성을 확인합니다. 일상 백업이면 manifest.json, 전체 백업이면 SHA256SUMS를 확인합니다.
  4. 백업의 DB 리비전과 사용할 서버 코드가 호환되는지 확인합니다.
  5. 첨부파일이 필요한 경우 같은 시점의 storage 백업도 준비합니다.

복구 대상 파일을 먼저 검사합니다. 경로는 실제 파일로 바꿉니다.

cd '/home/leemoon/바탕화면/d-ddeck_db'
backend/.venv-linux/bin/python deploy/sqlite_backup.py validate \
  '/실제/백업폴더/ddeck.db'

정상 검사는 출력 없이 성공 종료할 수 있습니다. 오류가 나오면 복구하지 않습니다.

10.2 SQLite DB 복구 명령

아래는 서비스 중지, 현재 상태 보관, 복구 대상 확인을 마친 뒤 실행합니다. 운영 DB를 변경하는 명령입니다. restore는 검사된 임시 DB로 교체하고 이전 WAL/SHM 파일을 정리하므로 단순 파일 덮어쓰기 대신 사용합니다.

cd '/home/leemoon/바탕화면/d-ddeck_db'
backend/.venv-linux/bin/python deploy/sqlite_backup.py restore \
  '/실제/백업폴더/ddeck.db' backend/ddeck.db

첨부파일 복구는 서버가 중지된 상태에서 기존 backend/storage를 별도 보관한 후 같은 시점의 백업본으로 교체합니다. 이름이 겹치는 파일을 무작정 합치면 삭제됐어야 할 파일이 남거나 DB와 파일이 어긋날 수 있습니다.

.env는 현재 서버를 유지하는 일반 DB 복구에서 자동 교체하지 않습니다. 서버 이전 등으로 복구할 때만 DB·첨부 경로와 비밀 설정을 검토하고 소유자와 0600 권한을 맞춥니다. SECRET_KEY가 바뀌면 재로그인이 필요할 수 있습니다.

10.3 복구 후 확인

cd '/home/leemoon/바탕화면/d-ddeck_db/backend'
env -u DEBUG -u DATABASE_URL -u ENVIRONMENT \
  .venv-linux/bin/python -m alembic current
env -u DEBUG -u DATABASE_URL -u ENVIRONMENT \
  .venv-linux/bin/python -m alembic check

구조 검사 실패 시 그대로 시작하지 않습니다. 새 코드를 유지하며 과거 DB를 복구하는 경우 백업 복제본에서 마이그레이션을 검증한 뒤 적용합니다. 이전 버전으로 완전히 롤백한다면 그 버전의 코드·의존성·DB·첨부를 함께 맞춥니다.

검증 후 시작하여 로그인, 주요 기록 건수, 최근 대응 내용, 사진·첨부 다운로드, 견적 PDF를 확인합니다. 견적서 마이그레이션을 downgrade하면 견적 테이블과 PDF가 제거될 수 있으므로 단순 장애 해결용으로 downgrade하지 않습니다.

기본 실행 예:

systemctl is-active ddeck

deploy/monitor.py는 표준 설치의 backups/last_success.json을 확인합니다. 현재 ddeck-restart 백업은 그 파일을 만들지 않으므로, 이 모니터를 그대로 실행하면 DB 백업이 있어도 No verified backup이 표시될 수 있습니다. 현재 환경에 자동 감시·원격 알림이 설치됐다고 가정하지 않습니다.

자동 백업을 새로 구성할 때는 --backup-only처럼 관리자 인증이 없는 백업 전용 명령을 사용하고 로그·실패 알림·보관 용량 정책도 함께 구성합니다. 대화형 재시작 명령을 그대로 cron에 등록하지 않습니다.

12. 다른 PC에 새 서버 설치할 때

새 PC에 표준 설치하려면 Ubuntu 설치 안내를 따릅니다. 예를 들어 1.0.13 설치 파일을 내려받아 다음처럼 실행합니다.

chmod +x ddeck-server-1.0.13.run
sudo ./ddeck-server-1.0.13.run

표준 설치는 /opt/ddeck, 전용 서비스 계정 ddeck을 사용하고, 기본 DB는 PostgreSQL입니다. 현재 바탕화면 SQLite 설치본과 백업·복구 명령이 다릅니다. 설치 옵션과 기존 서버 이전 절차를 확인한 뒤 실행합니다.

구분 현재 설치본 표준 설치본
경로 사용자 바탕화면 프로젝트 /opt/ddeck
실행 사용자 leemoon ddeck
가상환경 .venv-linux .venv
DB SQLite 기본 PostgreSQL, SQLite 옵션
일상 백업 ddeck-restart --backup-only sudo bash /opt/ddeck/deploy/backup.sh

업데이트 이 문서 6장 표준 설치 갱신 절차

외부 접속이 필요하면 VPN 또는 HTTPS와 접속 제한 정책을 함께 구성합니다. 서버를 인터넷에 직접 노출하기 전에 VPN 안내를 확인하세요. 현재 사내 HTTP 주소만으로 외부망 접근이 된다고 가정하지 않습니다.
