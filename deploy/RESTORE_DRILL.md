# 백업·갱신·복원 점검

## 갱신

Ubuntu에서 새 `.run`을 다시 실행하면 기존 `.env`와 systemd 유닛을 확인해
`update.sh` 경로로 들어갑니다. 기존 포트·설정을 유지하며 서비스 중지 → 백업 →
코드·의존성 교체 → 스키마 확인/마이그레이션 → 시작 순서로 진행합니다.
백업 실패 시 코드 교체 전에 중단하고 기존 서비스를 다시 시작합니다.
코드 교체 이후 실패 시 서비스를 중지하고 백업 위치를 안내합니다.
DB만 자동 롤백해 새 코드와 섞는 방식은 사용하지 않습니다.

Windows 재설치도 기존 작업과 설정을 확인하고 중지·백업 후 교체합니다.
작업 종료 후 uvicorn 프로세스가 남아 있으면 교체를 중단합니다.
다른 프로세스가 포트를 사용 중인 경우는 계속 오류로 처리합니다.
Windows 실제 설치·작업 스케줄러 동작은 해당 OS에서 별도 검증해야 합니다.

설치본에 유지되는 관리 스크립트 위치:

- Ubuntu: `/opt/ddeck/deploy/`
- Windows: `C:\ProgramData\ddeck\deploy\`

자동 백업은 이 경로의 스크립트를 등록합니다. 예전에 임시 설치 폴더 경로로
등록했다면 갱신 후 `backup.sh --install-cron` 또는 `backup-windows.ps1 -InstallTask`로 다시 등록합니다.

## 복원 동작

복원 스크립트는 압축 해제된 파일과 SQLite 무결성을 먼저 확인합니다.
그다음 서버를 중지하고 현재 DB·첨부를 별도 백업한 뒤 덮어씁니다.
현재 데이터 백업에 실패하면 복원을 진행하지 않습니다.
SQLite는 검사된 임시 복사본을 준비하고 기존 `-wal`/`-shm`을 제거한 뒤
DB 파일을 교체합니다. 백업 실패 시 일반 파일 복사로 대체하지 않습니다.
복원 후 실패하면 서비스를 중지한 채 남겨 추가 변경을 막습니다.

Ubuntu 백업에는 `.env`도 들어갑니다. 복원은 현재 `.env`를 자동으로 바꾸지 않으므로,
서버 이전 시에만 백업에서 설정을 별도로 복원하고 파일 소유자와 600 권한을 맞춥니다.
현재 Linux/Windows 공통 ZIP은 `.env`·DB 리비전·서비스 설정·첨부·체크섬을 포함합니다. rclone 설정 시 원격 검증 후 정리하며 기본 최근 7개를 보존합니다(`KEEP_MIN`). 압축은 `.tmp` 완성·검증 후 최종 이름으로 바꿉니다. 예전 tar.gz도 복원 도구로 읽을 수 있습니다.

## 분기별 복원 연습

1. 운영 서버와 분리된 시험 PC/VM에 같은 버전 서버를 설치합니다.
2. 운영 백업을 시험 PC로 복사합니다. 시험 PC에서 외부 푸시·스케줄러를 끄고
   `.env`의 DB 주소가 시험 DB를 가리키는지 확인합니다.
3. 시험 데이터 한 건과 첨부를 등록한 뒤 백업 복원 명령을 실행합니다.
   Ubuntu는 `sudo bash /opt/ddeck/deploy/backup.sh --restore <백업.zip>`,
   Windows는 관리자 PowerShell에서 `backup-windows.ps1 -Restore <백업.zip>`입니다.
4. 복원 직전 시험 데이터가 담긴 백업이 새로 생겼는지 확인합니다.
5. 서버 기동, 로그인, 매장·대응 기록 건수, 첨부 다운로드, 최근 이동 이력을 확인합니다.
   backend 가상환경에서 `python -m alembic check`를 실행합니다.
6. 새 백업으로 시험 PC를 다시 복원해 3번에서 만든 데이터·첨부가 돌아오는지 확인합니다.
7. 수행 날짜·백업 파일명·건수·복원 소요 시간·실패 내용을 운영 기록에 남깁니다.

로컬 자동 검증은 `python deploy/test_sqlite_backup.py`와
`python deploy/test_update.py`입니다. 임시 폴더만 사용하며 실제 서비스나 운영 DB를 변경하지 않습니다.

## 2026-09-26 후속 업데이트 확인

- 앱과 서버를 함께 갱신합니다. 세션 보안 변경으로 기존 로그인은 다시 필요합니다.
- `TRUSTED_PROXY_IPS`에는 실제 프록시 주소/CIDR만 등록합니다. 기본값은 비어 있습니다. 직접 노출 서버는 비워 두고 uvicorn을 `--no-proxy-headers`로 실행합니다. 설치·갱신 스크립트가 이를 적용합니다.
- 인증 요청 제한은 단일 서버 프로세스의 메모리를 사용합니다. 여러 워커/서버로 확장하면 앞단에 공유 IP/계정 rate limiter를 구성합니다.
- 업로드는 Content-Length 및 chunked 수신 모두 서버에서 제한합니다. 프록시를 사용하는 경우 nginx `client_max_body_size 26m;`도 설정해 25MB 파일과 multipart 부가 데이터를 제한합니다.
- 마이그레이션이 중복 S/N을 발견하면 중단합니다. 백업 복제본에서 해당 종류·S/N을 확인한 뒤 운영 데이터의 중복을 정리하고 재실행합니다. 자동 삭제하지 않습니다.
- Android 키 준비와 CI Secrets 등록은 [Android 서명 절차](../docs/ANDROID_SIGNING.md)를 따릅니다.
