# 데이터베이스 스키마 관리

운영(`ENVIRONMENT=production`)에서는 앱 기동 시 `create_all`을 실행하지 않습니다.
배포 전에 서비스를 중지하고 DB를 백업한 뒤, 설치된 backend 폴더의 가상환경에서
아래 명령을 실행합니다. 개발·테스트 환경에서만 `create_all`을 허용합니다.

## 새 설치 또는 초기 리비전 DB

```bash
python -m alembic upgrade head
python -m alembic check
```

`846cbbc04086`은 초기 24개 테이블, `2cca8909675d`는 30개 테이블, `83c49d102fa1`는 세션 식별자와 활성 S/N 유일 인덱스입니다. 현재 리비전 `ecdd8d8aea3c`는 반복 일정, FCM 발송 대기열, 부품 차감량, 매장 활성 상태, 사진 분류, 이력 숨김 시각을 추가하고 중복 PK 인덱스를 제거합니다.
새 리비전은 같은 종류의 대소문자·양끝 공백을 제외한 중복 S/N이 있으면 데이터를 변경하지 않고 중단합니다. 중복을 검토·정리한 뒤 다시 실행하세요.
추가 리비전은 매장·세트·대응 원인·대응인원·근무일지·임시저장 테이블 및
관련 컬럼을 생성합니다. 기존 장비의 세트 번호는 0, 기존 접수의 렌탈 여부와
회수 여부는 false로 채웁니다. 기존 행과 외래 키는 보존합니다.

## 이미 create_all로 현재 스키마를 만든 DB

현재 테이블이 있으나 Alembic 기록이 없거나 초기 리비전에 머물러 있는 DB는
바로 `upgrade head`하면 테이블 중복 오류가 납니다. 서비스 중지·백업 후 다음을 실행합니다.

```bash
# 읽기 전용: 모델과 실제 DB의 테이블·컬럼·인덱스·제약·기본값 비교
python scripts/adopt_schema.py
# 비교가 완전히 일치하는 DB에만 리비전 기록
python scripts/adopt_schema.py --stamp
python -m alembic upgrade head
python -m alembic check
```

검사 실패 시 `stamp head`를 직접 실행하지 마세요. 부족한 스키마를 적용하지 않고
완료했다고 기록하는 결과가 됩니다. DB 복제본에서 차이를 확인하고 별도 이관이 필요합니다.
도구는 현재 스키마 또는 검증된 `2cca8909675d` 스키마와 완전히 일치할 때만 해당 리비전을 기록합니다. 이후 `upgrade head`로 나머지를 적용합니다. SQLite가 자동 비교하지 못하는 표현식 인덱스도 별도 DDL 비교로 확인합니다.
갱신 스크립트는 서비스 중지·백업 후 이 검사를 실행하고, 완전히 일치하는 DB만 자동 등록합니다.
수동 배포에서는 위 절차를 직접 실행합니다.

## 검증

```bash
python scripts/test_migrations.py
```

임시 SQLite DB로 빈 DB 설치, 초기 스키마에 데이터가 있는 경우의 업그레이드,
다운그레이드 후 재업그레이드, 모델 일치 및 외래 키·무결성을 검사합니다.
릴리스 CI에도 같은 검사가 포함됩니다. PostgreSQL 실환경 검증은 별도 과제입니다.
운영 DB의 다운그레이드는 새 테이블/컬럼의 데이터를 제거하므로 복구용 백업을 우선 사용하세요.

이번 세션 보안 변경 배포 후 기존 access 토큰은 다시 로그인이 필요합니다. 서버와 refresh 회전을 지원하는 앱을 함께 업데이트하세요.
